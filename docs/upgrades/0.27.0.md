# Upgrade: CommandTower 0.27.0

**From:** `0.26.0`  
**To:** `0.27.0`

Minor release: inbox lifecycle and freshness. The platform now has one unread number everywhere, every inbox mutation returns the server count, reminders can resolve themselves, impersonation is audited and delete is refused, and push gains an optional collapse key and an optional badge-only sync. Everything is additive: two new columns, new endpoints, new options that default to today's behaviour. Contract: [API reference](../api_reference.md#me-inbox) and the [messaging guide](../messaging_integration_guide.md).

## Migrations (required)

Two additive migrations. Hosts must install and run them before the new code serves traffic:

```bash
bin/rails command_tower:install:migrations
bin/rails db:migrate
```

| Migration | Change |
|-----------|--------|
| `20261127000000_add_resolved_at_to_messaging_inbox_items.rb` | `messaging_inbox_items.resolved_at` (nullable, no index) |
| `20261127000001_add_collapse_key_to_messaging_communications.rb` | `messaging_communications.collapse_key` (string, limit 64, nullable) |

Both are in the install baseline (`ENGINE_MIGRATION_BASENAMES`), so the doctor reports a host that has not copied them.

**What breaks without them:** inbox reads, counts and mutations select `resolved_at`, so every `/me/inbox*` request fails with a database error (`500`) once the new code runs against the old schema; producing or accepting a communication writes `collapse_key` and fails the same way. Run the migrations in the same deploy as the bump, and migrate before new nodes take traffic (see Rolling deploy).

## Host-visible changes

| Change | Host impact |
|--------|-------------|
| One number rule | `badgeCount` always equals `count`, and the push `badge` is the same number for every notification type. Consequence for the iOS app icon: a type declared `badge_eligible: false` used to stay out of the icon number; it now counts, so the icon can show a higher number than before. |
| `badge_eligible` deprecation | The keyword on a notification type declaration is still accepted and is ignored. It will be removed in a future major release, once no host passes it. Remove it from your declarations when convenient. |
| Global unread rule | The global count, the push badge and mark-all-read count items that are not viewed, not archived, not deleted and not resolved (`counts_as_unread`). |
| List and thread unread rule | `InboxItem.unread_in_scope`: list rows and conversation entries count unread within the list scope (Inbox or Archived). A row can be unread in Archived without counting toward the global number. List rows add `notificationTypeKey` and `unreadInboxItemIds`. |
| Resolve | `Messaging::Contract::Inbox.resolve_for_event` / `unresolve_for_event` set or clear `resolved_at` per recipient. A resolved item leaves the list, the count, the badge and unread paths, and a conversation whose members are all resolved returns `404`. Show and open still work by id. Hosts decide when to call it; the engine never parses `host_event_identity`. |
| `meta.unreadCount` | `{ count, badgeCount }` on open, archive, delete, views, mark-all-read and every `bulk/*` response. `data` shapes are unchanged. |
| New endpoints | `POST /me/inbox/views` (passive scroll-read, batch of 1 to 100 ids) and `POST /me/inbox/mark-all-read` (`upTo` watermark). |
| `no-store` | `GET /me/inbox/unread-count` sends `Cache-Control: no-store`. There is no ETag or 304 on it. |
| Delete under impersonation | `DELETE /me/inbox/:id` and `POST /me/inbox/bulk/delete` return `403` `inbox_impersonation_forbidden` while impersonating. Clients that call delete during impersonation must handle it. |
| Impersonation audit | Archive, restore, `bulk/read`, `bulk/unread`, `bulk/archive`, `bulk/restore` and mark-all-read are allowed while impersonating and emit one `messaging_inbox_changed_while_impersonating` event per request, in the same transaction as the change (retention one year, ids-only metadata, not in account history). Views record nothing while impersonating and answer `skipped: "impersonating"`. See [Audit](../audit.md). |
| `config.messaging.inbox.restore_archived_thread_on_new_message` | Default `false` (archived threads stay archived). When `true`, a new message with a `conversation_key` restores the recipient's archived, non-deleted, non-resolved items in that conversation. Restoring brings back archived unread members, so one new message can raise the badge by more than one. |
| `config.messaging.inbox.badge_sync_push` | Default `false` (no push is sent). When `true`, a count-changing inbox action enqueues a silent badge-only push (`{to, badge}`) after commit, never while impersonating. Needs the Expo `http` adapter. Delivery on a device is an owner device check; do not enable it on a host until that check passes. |
| `collapse_key:` on Produce and Accept | Optional, 64 characters at most, sent to Expo as `collapseId`. Not fingerprinted and never derived from `conversation_key`. iOS replaces a delivered notification with the same key; Android behaviour follows Expo/FCM and is not guaranteed. **Shared-key warning:** every push with the same key collapses into one on that device, across types and conversations. Namespace keys (for example `<type>:<entity_id>`) and never share a key between unrelated notifications. See [Push collapse key](../messaging_integration_guide.md#push-collapse-key). |

## Host actions

1. Bump the gem to `0.27.0` (or `>= 0.27.0`) and run `bundle install`.
2. Run `command_tower:install:migrations` and `db:migrate` (above), commit the copied migrations and the schema change.
3. Nothing else is required: with no new options set, a host behaves as on 0.26.0 apart from the one-number rule and the `meta` / `no-store` additions.
4. Optional, by host choice: call resolve/unresolve for self-clearing reminders, set `collapse_key` where a newer push should replace an older one, set `restore_archived_thread_on_new_message`, set `badge_sync_push` after the device check.
5. Clients: `@commandtower/frontend` `0.7.0` is the paired release. It reads `meta.unreadCount`, calls `views` and `mark-all-read`, and falls back to per-item open and a hidden Mark all read when the engine answers `404` (an engine older than 0.27.0). It installs a single app `focusManager` for refresh on focus and the 15 s unread poll; a host that registers its own React Query `focusManager` handler should drop it. Pair the client release with this engine release.

## DoubleFloor Me pin advice

DoubleFloor Me keeps its gem pin at `~> 0.26.0` until its own bump to `0.27.0` is planned and its owner device checks and migrations are in hand. Pin it before this release is pushed to the gem index, so a routine `bundle update` cannot pull `0.27.0` into DFM without its migrations. Pick'em and DFM bumps are host work and ship after this release (platform release first, then host bump).

## Rolling deploy

Run the migrations before new nodes take traffic. The columns are nullable and additive, so old nodes keep working against the migrated schema; new nodes against the old schema fail (see Migrations). Behaviour options default to off, so mixed fleets agree until a host flips one.

## Not in this release

- No ETag or `304` on `GET /me/inbox/unread-count`; it sends `no-store`.
- No batch resolve, and no host sweep or backfill of `resolved_at`.
- No `PATCH /me/inbox/:id/restore`; `POST /me/inbox/bulk/restore` with one id covers it.
- No change to authentication, sessions, CSRF or RBAC.
