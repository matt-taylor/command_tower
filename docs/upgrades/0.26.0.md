# Upgrade: CommandTower 0.26.0

**From:** `0.25.0`  
**To:** `0.26.0`

Minor release: experience-states hardening. `POST /me/experience-states/complete` now only accepts keys the host registered, and it is rate limited, capped and refused while impersonating. Contract: [API reference](../api_reference.md#experience-states). No migration.

## Host-visible additions

| Change | Host impact |
|--------|-------------|
| `config.registry.experience_states.register "key", scope_types: [...]` | **Required.** Any key or scope type not registered is refused with `422` `experience_state_unregistered`. CommandTower seeds no keys. |
| `max_rows_per_user` (250), `complete_rate` (`{ limit: 30, window: 60 }`) | Composers on the same registry. Over the cap: `422` `experience_state_limit_reached`. Over the rate: `429` `experience_state_rate_limited` with `errors[].details.retry_after_seconds`. |
| Impersonation | `POST complete` while impersonating returns `403` `experience_state_impersonation_forbidden`. |
| Boot check | `host_key` set and the registry empty raises at boot in the test environment and logs an error in development and production. |
| Audit | `experience_state_completed` now has retention `one_year` (was `permanent`) and carries metadata `experience_key` and `version`. See [Audit](../audit.md). |
| `Services::Account::ExperienceStates::Completed` | Read-only completion check. See [Extending](../extending.md). |

`GET /me/experience-states` and the stored rows are unchanged.

## Host actions

1. **Register every key before bumping.** Add `config.registry.experience_states.register` for each key the product (or its client) completes, in the same deploy as the bump or earlier. A client that completes a key the host has not registered gets `422` from the first request after the bump. See [Bootstrap 08](../bootstrap/08-initializer.md#experience-state-keys).
2. **Pick'em** must register `welcome` and `competitive_league` before, or in the same deploy as, its gem bump. The enforcing check is pickem-api `spec/requests/api/me/experience_states_spec.rb`.
3. Bump gem to `0.26.0` (or `>= 0.26.0`) and run `bundle install`. No `db:migrate` is needed for this release (the `0.25.0` device-sessions migration is separate).

## Local stacks

A local stack that path-mounts the gem runs the new code immediately. Until the host initializer registers its keys, its test environment fails at boot (empty registry) and other environments log an error and refuse every complete with `422`. Register the keys first.

## Known residual

An impersonating admin is refused on `POST complete`, but `GET /me/experience-states` still returns the impersonated user's facts (read only, as for other `/me` reads).

## Operator recipe: read a user's completed facts

Read-only, per user. There is no delete path; a completed fact is undone only by the host choosing a new `version` for the key.

```ruby
CommandTower::UserExperienceState
  .where(user_id: user.id, host_key: CommandTower.config.application.host_key)
  .order(:completed_at)
  .pluck(:experience_key, :scope_type, :scope_identifier, :version, :completed_at)
```

Run it from a console or a reporting query. Do not write to the table. First creations are also in the audit ledger as `experience_state_completed` for one year.

## Rolling deploy

No schema change, so order only matters for registration: old nodes accept any key, new nodes accept registered keys only. Register keys in the release that bumps the gem.

## Not in this release

- No delete or reset endpoint for experience-state facts.
- No change to authentication, sessions or CSRF.
